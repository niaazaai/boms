screen specs. The finished visual layer lives in [`specs/design/`](../design/).

## Regenerate

```bash
python3 .agent/scripts/wireframes/build.py
python3 .agent/scripts/wireframes/build.py --coverage   # untranslated strings
```

Everything is generated from Python — never hand-edit the `.excalidraw` JSON,
it is overwritten on every build.

```
.agent/scripts/wireframes/
  dsl.py              tokens, primitives, components, shells, barcode/QR, mirror()
  i18n.py             Dari and Pashto string tables + localise()
  build.py            writes every file, including the localised boards
  modules/
    overview.py       sidebar system · module map · sitemap · corrections
    platform.py  inventory.py  procurement.py  sales.py  finance.py
```

## Reading a board

Boards are laid out **section by section**, each section starting on a fresh
row, and screen ids carry their section. The Inventory board reads:

| | Section | Screens |
|---|---------|---------|
| **A** | Dashboard | A1 |
| **B** | Items | B1 list · B2 new drawer · B3 edit drawer · B4–B9 the six profile tabs |
| **C** | Stock ledger | C1 ledger · C2 stock-in · C3 receive PO · C4 adjust · C5 dispose |
| **D** | Reservations | D1 list · D2 reserve drawer · D3 availability calendar |
| **E** | Transfers | E1 list · E2 transfer drawer |
| **F** | Reports | F1 valuation · F2 movement · F3 rental ROI |

The same ids are used in [`specs/features/03-inventory.md`](../features/03-inventory.md)
and [`specs/design/`](../design/), so a screen can be traced across all three.

## Conventions

### Annotation
Every screen carries a **note box** stating exactly what it reads and writes,
using real table names. These notes are the contract between the wireframe and
[`specs/database/`](../database/) — if a screen and the schema disagree, the note
is where the disagreement shows up. Notes are not UI and are not translated.

### UX rules
- **Every create and edit is a drawer / offcanvas over its list**, with its own
  title and subtitle. A list and its form never share a page.
- **No invite feature** — users are created directly inside a tenant
- **Language is a tenant setting** (English · Dari · Pashto). The switcher names
  the language and **never shows a direction badge**.
- Dari and Pashto mirror the whole shell; numbers, SKUs, barcodes and dates stay
  left to right. Barcode and QR symbols are never mirrored.
- Posted documents show **Void**, never Edit

### Inventory item rules
- **Barcode is generated from the SKU** (Code 128), never typed, and a QR with
  the same payload sits beside it on the item profile (ADR-014)
- **No `purpose` field** — sellable = has a sale price, rentable = has a rental
  price (ADR-013)
- **No fixed rental period** — the dates come from the booking (ADR-013)

### Data model shown
The **corrected** model from [`specs/review/02-decisions.md`](../review/02-decisions.md):

- Owned = on hand + on rent — valuation uses owned
- Reservations are not ledger rows
- Weighted average cost
- Deposits are a liability, shown separately from income
- Rental amortisation as its own COGS line
- Landed cost visible on every receipt
